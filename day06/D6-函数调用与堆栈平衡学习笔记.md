## 1. call / ret：便利贴机制（基础中的基础）

**类比**：你正在读一本书，读到一行"翻到第 20 页去执行炒鸡蛋"。你怕炒完忘路，就拿便利贴写上"炒完回第 3 页的下一行"，压在手边，然后翻过去干活。干完，撕下便利贴，照地址翻回去继续读。

| 指令 | 做的事 | 一句话 |
| --- | --- | --- |
| `call` | ①把"执行完 call 之后该回哪一行"（返回地址）压到便利贴堆最上面 ②跳进函数 | **记录 + 跳走** |
| `ret` | 撕下便利贴堆最上面那张，看地址，跳回去继续 | **撕便利贴跳回** |

- 这一摞便利贴就叫**栈（stack）**。
- 为什么是一摞？因为函数里还能再调函数（嵌套），一层层贴上去，返回时一层层撕下来。**最后贴上去的，最先撕下来 = 后进先出（LIFO）**。

> ✅ 口头验证（已答对）：call 做了记录返回地址 + 跳走两件事；ret 做撕便利贴跳回一件事。

## 2. 参数传递：端菜上桌（从右往左）

**类比**：去 add 家做客得带东西，参数 3 和 4 就是带的菜。怎么带？**call 之前先把它们放到栈上**（放上去的动作叫 `push`）。

调用 `add(3, 4)` 的顺序：

```
push 4      ; 第二个参数，先放
push 3      ; 第一个参数，后放
call add    ; 压返回地址，跳进函数
```

放完，栈从上到下：

```
[返回地址]   ← call 刚贴的（最上面）
[参数1 a=3]  ← 紧挨返回地址，最好找
[参数2 b=4]
[更早的东西…] ← 不关 add 的事
```

**为什么从右往左压？** 因为栈是 LIFO（后放的在上）。想让"第一个参数"永远贴死在返回地址正下方，就得让最后一个参数先放、第一个参数最后放。这样**不管几个参数，第一个参数位置永远固定，函数不用猜**。

> ✅ 口头验证（已答对）：`add(3,4)` 先 push 4 再 push 3；栈是后进先出。

## 3. 谁收桌子：cdecl vs stdcall（今天核心）

**场景**：函数干完活返回了，但参数那两张便利贴还留在桌上。不收拾的话，每调用一次就多堆几张，栈越堆越高，最终乱套。**必须有人收桌子——谁来收？两种规矩。**

| | cdecl（C 语言默认） | stdcall（Windows API 默认） |
| --- | --- | --- |
| 谁收桌子 | **调用者（客人）收** | **被调用者（餐厅）收** |
| 调用侧反汇编 | call 之后跟着 `add esp, 8`（清 8 字节 = 2 个参数） | call 之后**没有** add esp |
| 函数结尾 | `ret`（不带数字） | `ret 8`（带数字 = 返回时顺带清 8 字节） |
| 符号名 | `_add_c` | `_add_s@8`（@8 = 参数总字节数） |
| 可变参数（printf） | 支持 | 不支持（参数个数必须固定） |

**识别口诀**：
- cdecl：调用后能看到 `add esp, N`；函数结尾是 `ret`（没数字）
- stdcall：函数结尾是 `ret N`（带数字）；调用后没有 add esp

## 4. ebp 记号笔：函数怎么找参数（栈帧）

**为什么要 ebp？** esp（栈顶指针）像"你的手"，随时会动（push 一下就挪）；拿它量参数位置不准。所以函数一进门，拿记号笔（ebp）在"返回地址"那层画个固定记号。

**函数标准开头两行**：

```
push ebp      ; 保存上一层的记号笔（出门前要还回去）
mov  ebp, esp ; 在当前位置画记号
```

**记号笔坐标（全背下来）**：

| 坐标 | 内容 | 说明 |
| --- | --- | --- |
| `[ebp+0Ch]` | 参数 2 | 往上数第 2 格 |
| `[ebp+8]` | **参数 1** | 往上数第 1 格 |
| `[ebp+4]` | 返回地址 | call 贴的便利贴 |
| `[ebp]` | 旧 ebp（记号点） | push ebp 存的 |
| `[ebp-4]` | 局部变量… | 往下是函数自己的地盘 |

**铁律：量参数永远用记号笔 `[ebp+…]`，不用手 `[esp+…]`**——esp 会动，ebp 固定。

**函数标准结尾**：`pop ebp`（还记号笔）+ `ret` / `ret N`（cdecl 不带数字 / stdcall 带数字）

> ✅ 口头验证（已答对）：`[ebp+4]` 是返回地址，所以第一个参数从 `[ebp+8]` 开始数。

## 5. 验收：默写 add 函数反汇编骨架（已通过）

**被调用者侧**（`int add(int a, int b) { return a + b; }`，32 位 cdecl）：

```asm
push ebp          ; 保存上层记号笔
mov  ebp, esp     ; 画记号
mov  eax, [ebp+8] ; 取参数1 (a)
add  eax, [ebp+0Ch] ; 加上参数2 (b)
pop  ebp          ; 还记号笔
ret               ; 回家（cdecl 不带数字）
```

**stdcall 只改一个数字**：`ret` → `ret 8`（餐厅收桌）

**调用者侧**（cdecl）：

```asm
push 4
push 3
call  add
add esp, 8        ; 客人收桌：清掉 2 个参数
```

## 6. 结构体 = 基址 + 偏移

汇编里没有"结构体"这个概念，只有**一块连续内存 + 固定偏移**。看到 `[寄存器+常数]` 的访问模式，基本就是结构体字段或数组元素。

`struct P { int x; int y; }` → x 在偏移 +0，y 在偏移 +4（int 占 4 字节）。

**传指针**（`sum_p(struct P *p)`）真实反汇编：

```asm
mov  eax, [ebp+8] ; 取出指针 p
mov  edx, [eax]   ; p->x   ← 偏移 +0
mov  eax, [ebp+8]
mov  eax, [eax+4] ; p->y   ← 偏移 +4
add  eax, edx     ; 返回 x+y
```

**按值传**（`sum_pv(struct P p)`）：8 字节结构体被拆成两个 int，直接当两个参数复制进参数区（`[ebp+8]`、`[ebp+0Ch]`）——这就是"按值传"在栈上的样子。大结构体传指针省的就是这次复制。

## 7. 真实产物证据（gcc -m32 -O0，objdump -M intel）

**默写 vs 真实**（`_add_c`）：

```asm
; 我默写的                    ; gcc 真实产物（_add_c）
push ebp                55       push ebp
mov  ebp, esp           89 e5    mov ebp,esp
mov  eax, [ebp+8]       8b 55 08 mov edx,[ebp+0x8]
add  eax, [ebp+0Ch]     8b 45 0c mov eax,[ebp+0xc]
pop  ebp                01 d0    add eax,edx
ret                     5d       pop ebp
                        c3       ret
```

gcc 内部只是多了"先把 a 挪到 edx"一步（顺序不同，等价），**骨架逐行一致**。

**cdecl vs stdcall 的铁证**（函数体完全一样，差别全在结尾）：

```asm
00000000 <_add_c>:
  55            push ebp
  89 e5         mov ebp,esp
  8b 55 08      mov edx,DWORD PTR [ebp+0x8]
  8b 45 0c      mov eax,DWORD PTR [ebp+0xc]
  01 d0         add eax,edx
  5d            pop ebp
  c3            ret            ; ← cdecl：不带数字

0000000d <_add_s@8>:
  55            push ebp
  89 e5         mov ebp,esp
  8b 55 08      mov edx,DWORD PTR [ebp+0x8]
  8b 45 0c      mov eax,DWORD PTR [ebp+0xc]
  01 d0         add eax,edx
  5d            pop ebp
  c2 08 00      ret 0x8         ; ← stdcall：ret 带 8，被调用者清栈
```

`_main` 里的传参痕迹（参数从右往左 + cdecl 侧清栈）：

```asm
mov DWORD PTR [esp+0x4], 0x4   ; 参数2 先写（等效先 push 4）
mov DWORD PTR [esp], 0x3       ; 参数1 后写（等效后 push 3）
call _add_c
mov DWORD PTR [ebp-0x4], eax   ; 返回值从 eax 取走存局部变量
```

## 8. 答辩题（含答案，用于自查）

1. **默写** `int add(int a, int b)` 的 cdecl 反汇编骨架 → 见第 5 节，已通过验收。
2. stdcall 相比 cdecl 有两处不同？→ ①函数结尾 `ret` vs `ret 8`（被调用者收桌 vs 不收）②调用侧 call 后有无 `add esp,8`（调用者不收 vs 收）；另有符号 `@8` 特征。
3. 为什么 `[ebp+8]` 是第一个参数而不是 `[ebp+4]`？→ `[ebp+4]` 是返回地址（call 压的便利贴），第一个参数在它正上方一格。
4. 为什么 printf 必须是 cdecl？→ 参数个数可变，只有调用者知道压了多少张便利贴，只能由调用者收桌（stdcall 的 `ret N` 需要参数个数固定，写死收多少）。
5. `sum_p` 里 `[eax]` 和 `[eax+4]` 是什么？→ 结构体指针 p 指向的 x（偏移 0）和 y（偏移 4）。

## 9. 踩过的坑（重点记住）

- **esp vs ebp 分工**：esp 是"手"（动），ebp 是"记号笔"（固定）。量参数用 ebp，绝不用 esp。默写时第一个版本把 `push/pop ebp` 写成 `esp`、取参写成 `[esp+8]`，全部由此纠正。
- **`pop eax` 是坑**：函数结尾 `pop ebp` 还记号笔；`pop eax` 会破坏返回值（eax 是带结果回家的专用口袋）。
- **32 位才有 cdecl/stdcall 之争**：x64 下统一走寄存器传参（rcx/rdx/r8/r9），没有这两种约定的差异；但 32 位程序、32 位 Windows API、大量恶意样本仍是 cdecl/stdcall 世界，所以必须会。

## 10. IAT：程序的电话本（实战完成 2026-09-17）

**IAT = Import Address Table，导入地址表**——程序的一张"电话本/通讯录"。
一句话定义：**地址表，用来查（函数）地址**。

**为什么需要它：**
- 程序调 API（如 MessageBoxA）时，函数代码不在 exe 里，在系统 DLL（user32.dll）
- DLL 每次加载的地址会变（ASLR 随机化），不能写死地址
- Windows 在程序启动时查好所有导入函数的真实地址，填进 IAT；程序运行时**查表取地址再 call**

**类比**：手机通讯录——你不背电话号码（记不住、会换号），通讯录存着号码，打电话 = 打开通讯录点名字。程序不记函数地址，IAT 存着，调用 = 查表拨号。

**反汇编特征**（64 位，`demo_iat64.exe`，objdump 反汇编）：

```asm
; main 里调用 MessageBoxA（注意 x64 前 4 参数走寄存器 rcx/rdx/r8/r9）：
mov  ecx, 0                        ; 参数1 hwnd = NULL
lea  rdx, [rip+0x2b5d]             ; 参数2 文本
lea  r8,  [rip+0x2b5c]             ; 参数3 标题
mov  r9d, 0                        ; 参数4 MB_OK = 0
mov  rax, QWORD PTR [rip+0x6f4d]   ; ★ 从 IAT 槽位 0x140008410 读出地址（objdump 标为 __imp_MessageBoxA）
call rax                           ; ★ 间接调用 = 翻表拨号
```

**导入表**（`objdump -p demo_iat64.exe`）：

```
DLL Name: USER32.dll
vma: 00008410  MessageBoxA    ← 基址 0x140000000 + RVA 0x8410 = 0x140008410
```

**运行时验证**（`demo_iat_runtime.py`，用 python ctypes 模拟加载器）：

```
MessageBoxA 的真实地址 = 0x7FF8A4CB6E40   ← 加载器会填进 0x140008410 的值
ctypes.WinDLL("user32")  ＝ Windows 启动程序时加载 user32.dll
取 MessageBoxA 地址       ＝ GetProcAddress（加载器查表）
弹窗成功                 ＝ 程序执行 call [IAT] 的效果
```

**证据链三视角（同一件事）**：反汇编 `call [0x140008410]` → 导入表 `USER32!MessageBoxA` → 运行时 `0x7FF8A4CB6E40`。

**为什么病毒/逆向盯 IAT：**
- IAT = 程序的通讯录，扫一眼就知道程序会干嘛：调了 `CreateFile`（读写文件）、调了 `WriteProcessMemory`（写别人内存）……
- **IAT hook**：把表里的地址偷偷换成病毒代码的地址，程序一拨号，先打进病毒。

**实操文件**（本目录可复现）：`demo_iat.c`（源码）/ `demo_iat64.exe`（64 位编译产物）/ `demo_iat_runtime.py`（运行时地址模拟）。
